## 2. How Tony calls the six: sync vs async
Why v8 was async (three causes, with evidence):
1. Token. In v8 the operation runs with the caller's `access_token` only, with no service-account token: `callerOnly = events.every(e => e.context.secrets.access_token && !service_account_token && !snap_in_id)` -> `operation()` (`TC/dist/native.js:1039-1040`). Its scopes are the operation `static_scopes`, which v8 made read-only on purpose (`TC/manifest.yaml:303-307`). So the operation could not write TMX rows. It wrote a `command:` row through a signed POST to its own webhook source (`native.js:729-733`, `postControl` `native.js:222`), and the authenticated dispatcher wrote the row (`native.js:736-756, 1046`).
2. Provenance. v8 required every row to be created and modified by the service account and rejected other writers as tampering (`native.js:741-743`; pitfall "403 on custom-objects.update", `PB/tony-coordinator-pitfalls.md`).
3. Ordering. The queue serialized commands via `sync_id` (`TC/manifest.yaml:218`). It was not a function timeout: the function allows 120 s (`manifest.yaml:281`) and each fetch is capped at 25 s. The 15 to 226 s waits were the queue and dispatcher (`TS/28-handoff-work-engine-build.md:56`, `TS/21-work/B-live.md:60`).
Can the step return the engine answer synchronously? Yes for the step mechanics: workflow 55's operation step returned its output in the same call and a `set_ai_agent_skill_output` step put it in `body` (`TS/21-work/B-live.md:55-60`; manifest `result: struct`, `native.js:664` `output()`). What is UNPROVEN is that the operation token can write custom objects. Decision rule:
- Primary (S3 proves it): `work_engine_call` declares write `static_scopes`, builds the engine with `PlatformStore` on the caller token, runs the call, returns `Answer` as `result`. No queue, no polling, no result skill.
- Fallback if S3 shows 403: the operation does what v8 did (signed POST to a webhook event source, dispatcher runs the engine with the service-account token), and waits in-process up to 20 s polling the result row, else returns `{status:"queued", receipt}` plus one `work_result` skill. That adds a webhook source and `sync_id` serialization and reuses `TC/dist/native.js:222-233, 736-773`.
- Either way the engine stays correct without serialization, because CAS (section 3) is the only ordering it relies on.
Six skills, not one with an enum. Each workflow has 2 to 8 typed fields and a model-facing description taken from the `references.md` table. v8's single skill with 44 fields mapped 36 of them and turned omitted text into `""` (`B-live.md:55`). Each workflow has 4 steps, copied from workflow 55 (`B-live.md:49-57`): (1) agent skill trigger with the typed fields; (2) "Platform agent context" copying `agent_session_id` and `skill_call_id` from hidden platform metadata, which Tony cannot set (`B-live.md:51`); (3) operation `work_engine_call` with literal `call` and literal `snap_in_id`, `agent_session_id` and `request_id = skill_call_id` by jsonata (omitted optional fields stay absent, `B-live.md:55`); (4) `set_ai_agent_skill_output` with `body = $get('op','output')`. Workflows are not functions or packages, so quota is unaffected. Build them by cloning live workflow 55 (`PB/tony-coordinator-deploy-recipes.md`, "Workflow clone"): `templates.generate`, edit both template formats, `instantiate`, `components.validate`, `update-status active`.
`agent_session_id` path (D1): skill trigger metadata -> step 2 -> operation input -> `ai-agent.sessions.get` inside the function (section 4). The engine never sees a caller-set DM. Dedupe: `request_id` is the platform `skill_call_id`; engine calls are already idempotent on (job, action, ref) and claim keys, so a `max_retries` re-run is safe.
Latency budget: a call does about 10 to 40 store round trips at 0.2 to 0.5 s. Keep an engine call under 25 s and log its duration into every `Answer.timing` from day one. Risk: the skill step may have its own timeout that v8 never hit (its calls returned in under a second). S3 measures a real `checkpoint`.

## 3. Store: `work_record`, `work_event`, and `putIfVersion`
Types exist with 0 fields and 0 rows (scout: fragments 43 and 44). Fields per `docs/record-shapes.md`: `unique_key`, `kind`, `job_key`, `state`, `body`, `created_at`, `updated_at`, `version`; event adds `source`. v8 stored its JSON as a text field `tnt__state_json` and fell back to `description` (`native.js:139-148`). If a `json` field type is not accepted, use text and `JSON.parse` on read. Row title = unique_key (`native.js:296` pattern), `shared_with` the read-only role so the owner can read in the UI (`native.js:286-299`).
Key: `work-engine:qa:tony:<kind>:<id>` from `makeKey` (`src/store.ts:21`). The adapter appends `@v<N>`. Mapping:
| Store call | Platform |
| --- | --- |
| `putIfAbsent(k,v)` | `custom-objects.create unique_key=k@v1`; 409 means exists, then return the latest. (PROVEN-v8: `native.js:296, 309, 330, 769` treat 409 as "already there".) |
| `putIfVersion(k,v,N)` | `create k@v<N+1>`; 409 -> `{ok:false, version: latest}`; success -> `{ok:true, version:N+1}`. Version 0 means absent so `N+1 = 1`. |
| `put(k,v)` | read latest N, then the CAS create; retry on 409 up to 8 times (the engine's own limit, `src/engine.ts:152`). |
| `getVersioned(k)` | latest existing version (below), returns its body and N. |
| `getManyVersioned` | up to 100 keys per `objects.list` DQL `unique_key in [...]` (`record-shapes.md` reading rule, `TS/28:38-48`); UNPROVEN by me, the owner stated it. |
Finding the latest: versions are dense (a version is only created after reading its predecessor), so existence is monotone. One `objects.list` probes `@v1,2,4,8,...,256` and then a binary search narrows it: about 9 keys and 1 to 3 calls. Cache (key -> N) per invocation. No hint row and no updates, so there is no "viewer-only cannot update" trap (`PB/tony-coordinator-pitfalls.md`) and the writer identity can differ between calls.
Why this is safe: only one creator can win `@v<N+1>`. A reader on stale data proposes an old N+1, gets 409, and the engine re-runs the whole call from a fresh read (`Conflict`, `src/engine.ts:152`). A lost update cannot happen. If the platform's unique_key check is eventually consistent, that is a hole and S2 exists to test it: 20 parallel creates of one key, exactly one 201.
Exposure (accept for the pilot, state in the readiness matrix): (a) no multi-row transaction, so a crash between the job write and an index write leaves a partial state; the engine already orders writes for recovery (`docs/engine-design.md`), and S2 injects a crash between two writes; (b) row growth, about one row per write, estimated 2k rows per release, no deletes in the pilot (if `custom-objects.delete` works, a retention sweep later keeps the newest 3 versions); (c) read-after-create lag could make the engine retry more; (d) rows carry Tony-visible text only in `body`, never raw private evidence beyond what the engine already stores.
Alternative, only if S2 shows create-if-absent is not atomic: a per-key lease using a second create-only row `lock:<k>:<minute>`; this is weaker and not recommended.
Check S2 also tries `custom-objects.update` with `object_version` as a precondition; if it exists and is atomic, swap `putIfVersion` to it (one row per key, no growth). Not assumed.

## 6. Ingest
Primary path, no connector change. The connector today cannot deliver what the engine needs: its poller drops bot authors (`SC/code/src/poller/poll.ts:112-119`, `qualifies` returns false for `message.user === botUserId`), its invoke skips its own bot (`invoke.ts:396`), it only follows threads that mention the bot and expires watches after 24 h (`poll.ts:8`), and it watches every channel the bot is in, including protected `C08TJE6SDME` (scout). So the work engine polls by itself:
- A `watch` index row list (create-only versions, section 3) lists `{channel, thread_ts, job, last_ts}` for every thread the engine links. The adapter adds a row after each `job_open` answer that links a thread.
- Each timer tick, for each watched thread in the allowlist: `conversations.replies {channel, ts: thread_ts, oldest: last_ts}` with the Tony bot token (keyring `tony_slack_token`), max 20 threads per tick (Slack tier 3), cursor advanced by CAS after `ingest` returns.
- Each message becomes `IngestEvent {source:"slack", delivery_id:"<channel>:<ts>", kind:"message", thread:"<channel>:<thread_ts>", sender_id: msg.user, sender_kind: msg.bot_id && msg.user !== own_bot_user ? "other_bot" : "human", attrs:{ts, text, metadata_event_type}}` (`src/types.ts` `IngestEvent`). The engine derives `own_bot` from `sender_id === ownBotUserId` (`engine.ts:1675`), so Tony's own posts reach `ingest` with their ts and the engine matches them to the open claim (`engine.ts:1707`). Dedupe is the engine's create-if-absent on (source, delivery_id).
- Harry's QA post and sign-off arrive as `other_bot` events with the sender id `U0C4YRX93PS`. The spec lists `harry_bot` (`workflows/desktop-release/spec.json`), so the sign-off is valid.

## 7. Sweep and timer
Same timer source as above. The function's timer path is: `timer.tick` -> `poll()` then `engine.sweep()` (v8 routed `timer.tick` to `relay` for its own supervisor, `TC/dist/native.js:1044`; the service-account token is present on this path, `native.js:1041-1043`). Cadence `* * * * *`; the engine's bucket is `sweepMinutes=5` (`src/config.ts`) so most ticks find nothing due. Ticks can overlap (no `sync_id` on a timer): safe because the poll cursor and the engine are CAS-based. `max_execution_time` 120 s bounds a tick: poll at most 20 threads, then sweep, abandon the rest for the next tick. The sweep's catch-up scan for long outages is bounded by `MAX_BUCKETS_PER_SWEEP` (`src/engine.ts:45`); the parked red-team L1 (clock skew, long outage) is accepted for the pilot. Overdue detection is proved in S7 by pausing the install (deactivate 10 minutes, reactivate, job still woken).
